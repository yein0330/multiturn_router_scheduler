# followup_v4 설계 (동결 기록)

- 지시서: 사용자 지시(2026-10-19) 0–7절.
- 범위: 단계 A(인터페이스 진단)와 단계 B(동일 상태 Follow/Deviate)까지. 지도학습·PPO·eval 실행은 하지 않는다.
- v3 관문 1 미달은 그대로 유지한다. 이번 실험은 별도 후속 진단이다.
- 표기: [측정] 실행·측정값, [추정] 비용 모델 계산값, [가설] 미검증 해석.

## 1절 감사 (실행 완료, 새 추론 없음)

결과: `results/audit_v3/audit_v3.json`, `tool_error_kinds.csv`, `router_input_audit.csv`

- v3 dev50 재계산: 300실행, 5,558호출, 캐시 예측 불일치 0, C1–C2 불일치 short 0/236, long 3/217.
- 도구 오류 1,455건 중 1,282건(88%)이 `unknown column 'None`이다(A 1,097, B 185).
  - 원인: filter 조건에 `column` 키 없이 열 이름을 키로 쓴 형태다(예: `{"hotel": "==", "value": ...}`, `{"state": "cancelled"}`).
  - T0 스키마는 `conditions.items`를 `{"type": "object"}`로만 두고, 구조는 설명문에만 적었다.
  - 환경 오류 메시지는 끝 따옴표가 잘린 "unknown column 'None"으로, 누락된 필드를 알려 주지 않는다. 이 처리 방식은 바꾸지 않는다.
- 같은 요청 안의 반복: 같은 오류가 반복된 요청·종류 묶음은 247/425, 최대 8회. 묶음당 1건으로 세면 425건이다.
- R0 라우터 입력: 호출 1,803건 중 629건(35%)에서 현재 사용자 요청이 창(직전 4개 메시지) 밖으로 빠졌다. 결정 시점 현재 메시지의 1,355건이 도구 결과이고, 도구 결과는 `ASSISTANT:`로 표시된다.
- 지연 정의: 세션 지연 = Σ(라우터 + 렌더링 + 모델 호출 + 도구 실행), 재계산 오차 0. 벽시계는 이보다 중앙값 0.42 s 길다(계측 포함). v1–v3와 같은 정의다.

## 단계 A (동결: 2026-10-19, 실행 전)

### 데이터
- v3 dev50에서 10세션: 시나리오 × 하위 유형 홀짝마다 sha256('v4A|'+session_id)이 가장 작은 세션(`configs/stageA_sessions.json`). 결과 정보는 쓰지 않았다.
- short/long 모두 실행한다. 과제·난이도·도구 반환·호출 예산은 v3 그대로다. 개발용 진단 데이터이며 최종 평가가 아니다.

### 조건 (`src/iface.py`)
- T0: v3 스키마 그대로.
- T1: 구조를 명시한 스키마. 환경의 정답·의미·오류 처리는 바꾸지 않는다.
  - `filter.conditions.items`: `{column, op(enum ==, !=, <, <=, >, >=, in), value}`, 셋 다 required
  - `aggregate.op`: enum(count, sum, mean, median, min, max, count_distinct)
  - `get_rows`·`submit`: 기본값과 허용 형식 설명
  - 사전 점검(`results/precheck_iface.json`): enum의 모든 연산자를 환경이 받아들인다. `column` 누락과 enum 밖 연산자는 거부한다. `value` 누락은 오류 없이 처리된다. 환경이 더 관대한 것이고 T0에도 있던 동작이므로 기록만 한다.
- R0: `src/mrp/router.py` 그대로.
- R1: 도구 호출형 분석 작업 설명, USER/ASSISTANT/TOOL 구분, 현재 사용자 요청 항상 표시, 최신 도구 결과 표시.
  - 모델 설명 문장은 R0와 같다. 출력·파싱·fallback(B)도 같다.
  - 입력 예산은 R0와 같다(요청 ≤ 1,200, 다른 메시지 4개 × ≤ 300토큰).
  - 사전 점검: v3 대화 1,803건에서 요청 표시 1,803/1,803. 프롬프트 토큰 R1 p95 678 / 최대 1,203(R0 1,411 / 2,070).
  - 여러 수정을 묶은 조건이며, 개발 결과를 본 뒤 수정하지 않는다.
- 주 조건은 T1/R1로 사전에 정한다. 최고 점수 조합을 사후에 선택하지 않는다.

### 실행
- 10세션 × 2문맥 × 2스키마 × {always_A, always_B, follow_R0, follow_R1} = 160회. seed 401로 섞어 실행한다.
- 정책 실행마다 세 서버의 캐시를 reset한다(세션 시계 밖).
- 실행기: `src/runner_v4.py`. v3 agent_runner와 같은 루프이며, 스키마·라우터만 인자로 받는다.
- 모델·서버 설정은 `configs/models.json` 그대로(R 0.90). GPU 작업은 `followup_v3/run_locked.sh`(flock)로 단독 실행한다.
- 예산: A/B 합계 최대 8,000호출, R 최대 4,000호출(단계 A+B 합산). 실행 단위를 시작하기 전에 잔여 예산이 단위 최대치(32호출) 미만이면 멈춘다.
- 측정 항목: 요청 정답률, 세션 성공률, 지연과 구성 요소, 모델·라우터 호출 수, 전환, 모델별 생성 길이·캐시 적중, 도구 오류율, 형식 오류를 겪은 요청 비율, 같은 요청 내 동일 오류 반복, 예산 소진율.
- 비교: 같은 세션 짝 비교. 구간은 세션 재표집(10세션이라 기술용).

### 단계 B 진입 중단 조건 (사전 고정)
- 스키마·환경 불일치(T1에서 enum 안의 값이 환경 오류를 낸 경우), 라우터 입력 예산 위반, 정보 누락(R1에서 요청 미표시)이 관측되면 단계 B를 시작하지 않고 보고한다.
- 캐시 예측 불일치가 0이 아니면 원인을 감사하기 전까지 멈춘다.
- A의 성능이 낮다는 이유로 과제나 모델 쌍을 바꾸지 않는다.
