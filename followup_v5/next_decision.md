# 다음 결정 (followup_v5 단계 0–2 이후, 사용자 확인 필요)

단계 3은 시작하지 않았다.

## 요약

- **S1**: A가 처음 같은 호출을 반복한 시점에 원 이력 그대로 B로 올리면, 그 요청 정답률이 0.03에서 0.46으로 오른다(같은 상태 68개). 이력 요약은 손해였고, A에게 반복을 알리는 것은 효과가 없었다.
- **S2**: R1의 요청 시작 결정은 B 필요 요청의 7–10%만 잡는다. 같은 프롬프트의 연속 점수(R1s)는 AUC 0.74로 훨씬 잘 순위화한다. 추가 호출도 없다.
- 둘 다 "같은 상태"·"오프라인" 수준의 증거다. 세션 정책으로 묶었을 때의 품질–지연은 아직 측정하지 않았다.

## 단계 3 실행안 (확인 시)

- 데이터: v4 단계 A의 10 dev 세션 × 2문맥, T1.
- 정책:
  - 기존 결과 재사용: 항상 A, 항상 B, R1 따름
  - 신규 실행: G(R1 따름 + 첫 반복 시 원 이력으로 B 상향, 요청 끝까지 B), Q(요청 시작 R1s 점수 ≥ −18.5면 B, 요청 안에서는 유지), Q+G
- 규모: 3정책 × 20 = 60실행, 약 1,100호출(A/B) + R1s 요청당 1회(약 240). GPU 약 30분.
- 비교: 요청 정답률, 세션 성공, 세션 지연, 요청 단위 사후 선택(51–52%) 대비 여지 회수율.

## 사용자 결정이 필요한 항목

1. **단계 3 실행 여부.** 위 안대로 할지, 규모를 바꿀지.
2. **단계 3의 스키마.** T1-full(지시서 기본)과 T1-min(0-a에서 B에 더 나음, A 효과 미측정) 중 무엇으로 할지. T1-min으로 바꾸면 항상 A·R1 따름 기준선도 새로 실행해야 한다(약 400호출 추가).
3. **Q의 임계값.** train에서 정한 −18.5(B 비율 약 56%)를 그대로 쓸지, 지연을 줄이려 B 비율 상한을 둘지. 상한을 두려면 train에서 다시 정해 동결한다.
4. eval 실행과 어댑터 학습은 단계 3 결과를 본 뒤 정한다.
