# followup_v2 설계: 최초 B 진입 시점 통제

- **동결 기록**: 실행 전 설계·설정·표본·코드는 [configs/v2.json](configs/v2.json)과 commit `a216e00`(2026-10-16 13:35 KST, GPU 실행 전)에 고정했다.
  - 이 문서는 그 내용을 사람이 읽을 수 있게 옮긴 것이며, 실행 후에 작성했다.
  - 동결된 정의와 다른 내용은 없다. 결과를 보고 임계값·표본·정책을 바꾸지 않았다.
- **성격**: 단계 A·B2·followup_v1 결과를 본 뒤 설계한 **사후 탐색**이다. 확증 실험이 아니다.

## 1. 질문

멀티턴 작업에서 큰 모델(B)로 처음 들어가는 시점을 조절하면 품질–지연 관계가 개선되는가? 그리고 그 효과는 짧은 문맥과 긴 문맥에서 다른가?

## 2. 고정한 것 (기존과 동일)

- 모델: A = Qwen3-1.7B, B = Qwen3-8B. revision, tokenizer, chat template은 configs/models.json 그대로다. 같은 서버 설정(vLLM 0.19.1)이다.
- 디코딩: greedy, max_tokens 1024, thinking 끔.
- verifier(S5만, 단계당 재시도 1회)와 숨김 evaluator(표 3개).
- 평가 세션: 50개(`data/eval/eval.jsonl`). 난이도·시나리오 라벨은 분석에만 쓴다.
- 새 모델 다운로드, 라우터 학습, 데이터 확장은 하지 않는다. 라우터 R은 이번 실험에 쓰지 않으므로 서버도 띄우지 않았다.

## 3. 비용 감사 (추가 추론 없음)

- 유효 실행 4개의 모든 호출을 세션 내 실제 순서(재시도 포함)로 분류했다: `first_call` / `first_switch` / `return` / `stay`.
- 같은 세션의 P4 − P2 지연 차이를 구성요소로 분해하고, 잔차를 검사했다.
- 결과는 [cost_audit.md](cost_audit.md)에 있다.

## 4. 주 실험: 고정 전환 정책

| 정책 | 첫 B 단계 | 실행 |
|---|---|---|
| BBBBB | 0 | 기존 P2 재사용(아래 점검 통과 시) |
| ABBBB | 1 | 신규 |
| AABBB | 2 | 신규 |
| AAABB | 3 | 신규 |
| AAAAB | 4 | 신규 |
| AAAAA | 5(없음) | 기존 P1 재사용(아래 점검 통과 시) |

- 규칙: 단계 s 이상이면 B, 아니면 A다. 재시도도 같은 모델을 쓰고, 한 번 B로 가면 유지한다. 라우터 호출은 없다.
- 각 정책은 자기가 생성한 응답과 verifier 메시지를 이력으로 쓴다.
- 조건: short/retain, long/retain.
- 신규 실행: 4정책 × 50세션 × 2조건 = 400회.
  - 세션마다 (정책, 조건) 8개 조합의 순서를 seed 31로 섞었다. 두 조건을 시간상 교차시켜 실행 시점이 조건 비교에 섞이지 않게 했다.
  - 실행마다 시작 시각을 기록했다.
- **기준선 점검**(실행 전 고정 규칙):
  - 대상: seed 20261020으로 고른 시나리오별 2세션(10세션). 정답 여부와 무관하게 골랐다.
  - 이 세션들에서 BBBBB/AAAAA를 두 조건으로 다시 실행했다(40회).
  - 재사용 조건: 단계 결과 동일이 38/40 이상이고, 조건별 지연 비 중앙값이 0.95–1.05면 기존 P1/P2 50세션을 재사용한다.
  - 미달이면 BBBBB/AAAAA를 50세션 × 2조건 모두 새로 실행해 새 기준선만 쓴다.
  - 재실행은 독립 품질 표본으로 세지 않는다.
- 비교 대상: 항상 A/B, 기존 P4·P6(두 조건), P10(followup_v1, short만 있음).

## 5. 동일 이력 분기 진단

- 표본: seed 20261021로 고른 시나리오별 2세션(10세션). 기존 P1(항상 A) 경로에서 골랐으며, 성공·실패나 전환 이득은 보지 않았다.
- 분기점: 작업 단계 1과 3의 첫 시도 직전. 조건은 short/retain, long/retain. 분기점은 40개다.
- 복원 절차:
  1. 로그로 대화 이력을 재구성하고, 렌더링한 prompt 해시가 로그와 같은지 확인한다.
  2. A, B 서버의 prefix cache를 reset한다.
  3. A가 분기 전에 받은 prompt를 순서대로 다시 보낸다(max_tokens 1). B는 비워 둔다.
  4. 첫 호출의 실제 적중이 기대값(A: 블록 단위 최장 공통 prefix, B: 0)과 같은지 기록한다.
  5. 복원 준비 시간(`prep_s`)은 경로 지연에서 빼고 따로 기록한다.
- 경로:
  - `stayA`: 남은 단계를 모두 A로 처리
  - `switchB`: 분기 단계부터 끝까지 B
  - 분기 이후에는 각 경로가 자기가 생성한 이력을 이어간다.
- 반복: (분기점, 경로)마다 3회, 매번 다시 복원한다. 전체 240회의 순서를 seed 41로 섞었다. 반복은 지연 측정용이며 품질 표본이 아니다.
- 숨김 평가 결과는 분석에만 쓰고, 경로 진행에는 쓰지 않는다.

## 6. 실행 원칙

- GPU 작업 전체는 `run_v2.sh` 하나가 배타적 `flock`(`.gpu_runner.lock`)을 잡고 실행한다.
- 시작 전에 GPU 1·2에 다른 프로세스가 없는지 확인한다.
- 서버는 이 스크립트가 띄운 A, B만 종료한다.
- 정책 실행 비용에 포함하는 것: 정책 실행 중 실제로 일어난 모델 호출, verifier, 재시도, 렌더링.
- 따로 기록하는 것: 격리용 캐시 reset(세션 시계 시작 전)과 분기 상태 복원 비용.
- 매 턴 캐시 적중 예측과 서버 관측치를 비교하고, 중복·잘림·오류를 검사한다.

## 7. 분석

- 같은 세션끼리 짝지어 비교하고, short와 long을 따로 보고한다.
- 구간은 세션 재표집, 시나리오별 층화 bootstrap(2000회)으로 구한다. 기술용이며, 템플릿을 공유하므로 실제 불확실성보다 좁을 수 있다. 비열등성은 선언하지 않는다.
- 세션별 사후 최선은 "이 여섯 정책 집합 내 사후 최선"으로만 부른다. 다음 두 가지로 보고하며, 품질과 지연을 가중합하지 않는다.
  - Pareto 집합 포함 횟수
  - 품질 우선 사전식(품질 최대 중 최저 지연)
